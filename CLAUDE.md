## 1. System architecture

**Stack**

| Layer      | Technology                                             |
| ---------- | ------------------------------------------------------ |
| Framework  | Next.js 16 (App Router) + React 19                     |
| Language   | TypeScript (strict)                                    |
| Styling    | Tailwind CSS v4 + shadcn/ui (Radix primitives)         |
| Database   | Supabase PostgreSQL                                    |
| Auth       | Supabase Auth (cookie sessions via `@supabase/ssr`)    |
| Security   | PostgreSQL Row Level Security (RLS)                    |
| Icons      | lucide-react                                           |

**Request / trust flow**

```
Browser ──▶ middleware.ts ──▶ Server Components / Route Handlers ──▶ Supabase ──▶ Postgres (RLS)
             (refresh session,     (requireProfile / requireRole      (anon key + user session)
              coarse auth gate)     server-side guards)
```

Authorization is enforced at **three layers**, in order of trust:

1. **Database RLS** — the real boundary. Every table denies by default.
2. **Server-side guards** (`requireProfile`, `requireRole`, `requireCapability`)
   — UX + defence in depth. Redirect unauthorized users.
3. **Middleware** — coarse "logged in / not" gate + session refresh only.

Never trust the client for authorization. UI role checks are cosmetic.

## 2. Supabase client architecture

There are **four** clients, one per trust boundary. Use the right one:

| Client                         | File                         | Key          | RLS  | Use in                              |
| ------------------------------ | ---------------------------- | ------------ | ---- | ----------------------------------- |
| Browser                        | `lib/supabase/client.ts`     | anon         | ✅    | Client Components                   |
| Server                         | `lib/supabase/server.ts`     | anon+session | ✅    | Server Components, Actions, Handlers|
| Middleware                     | `lib/supabase/middleware.ts` | anon+session | ✅    | `middleware.ts` only                |
| **Admin** (service-role)       | `lib/supabase/admin.ts`      | service-role | ⛔️   | Trusted server-only privileged ops  |

- The **admin client bypasses RLS** and is marked `import "server-only"` so the
  build fails if it is ever imported into client code. Always run your own
  `requireRole` / `requireCapability` check *before* using it.
- `getUser()` (not `getSession()`) is used for auth decisions — it revalidates
  the token with Supabase.

## 3. Coding standards

- **TypeScript strict**; no `any`. Prefer `type` aliases for DB row shapes
  (Supabase's generics require rows assignable to `Record<string, unknown>`;
  `interface` rows are NOT and will silently degrade query types to `never`).
- **Server Components by default.** Add `"use client"` only when you need
  interactivity (forms, state, effects).
- **Server-only modules** (`lib/auth/*`, `lib/supabase/admin.ts`) start with
  `import "server-only"`.
- **Authorize by capability, not by scattered role checks.** Add capabilities to
  `CAPABILITIES` in `lib/constants/roles.ts` and use `can()` / `requireCapability()`.
- **Styling:** Tailwind utility classes + `cn()` for conditional merges. Colours
  come from CSS variables (`globals.css`) — never hard-code hex in components, so
  theming and future Arabic RTL stay clean.
- **UI primitives** live in `components/ui` (shadcn). Compose, don't fork.
- **Imports:** use the `@/` alias. Group external → internal.
- **Naming:** files `kebab-case`; components `PascalCase`; DB columns `snake_case`.
- **Lint & build must pass** before a change is considered done:
  `npm run lint && npm run build`.

## 4. Database rules

- **Every table has RLS enabled** and denies by default. A table without a
  matching policy returns nothing — that is intentional.
- **Migrations are ordered and immutable.** Add a new `NNNN_*.sql` file; never
  rewrite a migration that has already run. Numbering: `0001`, `0002`, …
- **Enums are the source of truth for vocabularies** (`user_role`,
  `driver_status`, `audit_action`) and must stay in sync with
  `src/lib/constants/roles.ts` and `src/types/database.types.ts`.
- **`updated_at`** is maintained by the `set_updated_at()` trigger, not the app.
- **Role checks in policies** go through the `SECURITY DEFINER` helper
  `current_app_role()` (and `is_admin()`) to avoid RLS recursion on `profiles`.
- **New users** are auto-provisioned as `DRIVER` (least privilege) by the
  `handle_new_user()` trigger on `auth.users`. Promotion to any other role
  requires an admin (or the service role for bootstrapping the first admin —
  see `0005_seed_notes.sql`).

**Tables (Phase 1)**

- `profiles` — 1:1 with `auth.users`; `role`, `is_active`, contact info.
  Users may edit their own row, but `role`/`is_active` changes are blocked for
  non-admins by the `protect_profile_privileges()` trigger.
- `drivers` — driver roster; may link to a `profile`. Managed by Admin /
  Transport Supervisor; readable by Admin / Supervisor / Management (and a
  driver may read their own linked record).
- `audit_logs` — **append-only** trail (see Security rules).

## 5. Security rules

- **Service-role key never reaches the browser.** It exists only in
  `SUPABASE_SERVICE_ROLE_KEY` (no `NEXT_PUBLIC_` prefix) and is used only by
  `lib/supabase/admin.ts` (`server-only`). Anon URL/key are public by design and
  safe to ship — they are protected by RLS.
- **Audit log is append-only, guaranteed at the database level:**
  - No `UPDATE`/`DELETE` RLS policy → normal roles cannot modify history.
  - `BEFORE UPDATE` / `BEFORE DELETE` triggers `RAISE EXCEPTION` → even a
    BYPASSRLS connection (service role, table owner) **cannot** alter or delete
    a row. Rows can only be `INSERT`ed, never changed.
  - Audit inserts are written server-side with the **verified session actor** —
    the client can never spoof `actor_id`.
- **Sign out is POST-only** (`/auth/signout`) so it can't be triggered by a
  prefetch, link, or crawler.
- **Deactivated accounts** (`is_active = false`) are refused at
  `requireProfile()`.
- **The app is `noindex`** (internal system) via root metadata.
- **Secrets** live in `.env.local` (git-ignored). `.env.example` documents the
  shape. Never commit real keys.
- **Least privilege everywhere:** default role is `DRIVER`; capabilities grant
  access explicitly rather than denying exceptions.

## 6. User roles

Defined in `src/lib/constants/roles.ts` and the `user_role` DB enum.

| Role                   | Purpose                                                        |
| ---------------------- | ------------------------------------------------------------- |
| `ADMIN`                | Full control: users, roles, drivers, audit, all settings.     |
| `TRANSPORT_SUPERVISOR` | Operational owner of the transport domain (drivers, later trips/assignments). |
| `DRIVER`               | Field staff. Sees only what is assigned to them.              |
| `MANAGEMENT`           | Leadership: read-only oversight, reports, audit visibility.   |

**Capabilities (Phase 1)** — authorize against these, not raw roles:

| Capability         | Roles allowed                               |
| ------------------ | ------------------------------------------- |
| `MANAGE_USERS`     | ADMIN                                        |
| `MANAGE_DRIVERS`   | ADMIN, TRANSPORT_SUPERVISOR                  |
| `VIEW_DRIVERS`     | ADMIN, TRANSPORT_SUPERVISOR, MANAGEMENT      |
| `VIEW_AUDIT_LOGS`  | ADMIN, MANAGEMENT                            |

## 7. Project phases

- **Phase 1 — Foundation (this codebase).** Project setup, Supabase client
  architecture, authentication, RBAC, `profiles` / `drivers` / `audit_logs`
  schema with RLS + append-only audit, professional login, protected dashboard.
  **No Trips or Assignments yet.**
- **Phase 2 — Core management.** User management UI (admin), driver CRUD, audit
  log viewer, i18n scaffolding (Arabic + English, RTL).
- **Phase 3 — Trips & scheduling.** Trip definitions, vehicles, calendar.
- **Phase 4 — Assignments & dispatch.** Assign drivers/vehicles to trips,
  driver-facing views, notifications.
- **Later.** Reporting/analytics, mobile polish, exports.

When starting a new phase: add migrations (never edit old ones), extend
`CAPABILITIES`, keep the three-layer authorization model, and update this file.
